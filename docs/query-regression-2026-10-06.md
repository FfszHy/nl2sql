# 业务问数修复与验证记录

验证日期：2026-10-06。数据源为仓库生成的影院合成示例库；下述结论限于已核对的示例和配置，不是自然语言问数准确率基准。

## 修复范围

- 生成前核对渠道、会员等级等业务名称与实际数据库取值，附带净收款、去重购票人数及退款口径。
- 用可见 Schema 检查真实表、字段、别名和 CTE 来源；城市收入按影院所在城市归属，电影类型使用 `movies.genre`。
- 多个指标和各组排名要求合并成单条只读查询。多语句候选仍拒绝执行，仅当全部语句各自满足只读规则时允许重新生成。
- PostgreSQL 在只读事务内预检。可以修复的候选默认最多生成三次，每次重新校验；连接中断、超时和锁等待不会触发 SQL 重写。
- 两类配置的分组排名说明直接使用实际查询行，保留城市和组内顺序、金额、人数、订单数及明确对应的百分比；最多展示前 20 行。
- 数据库失败审计现在保存候选 SQL、具体错误、SQLSTATE 和 trace_id；回滚失败不会掩盖原错误。

## 尚未确认的失败

追加验证期间，城市原问曾有一次请求在三次生成后仍返回数据库预检失败。该次客户端没有保存错误正文，旧审计也未记录数据库失败的候选 SQL，因此无法确定具体原因，不能声称已经定位或消除该次故障。

随后补全数据库失败审计，并保留客户端错误正文；同问题直接执行一次、HTTP 执行一次，以及追加三次 HTTP 复测全部成功。追加三次都在首次生成完成，15 行数据、顺序、金额、占比和图表逐次通过核对。最终说明代码也用这些实际结果及两种会员问法复核，未调用回答模型。

目前没有该失败再次出现的证据。若再次出现，日志可以区分字段或类型问题、连接问题及超时；修复次数仍然有界。上述成功结果不构成所有复杂问法都不会失败的保证。

## 后续系统优化与本轮验证

新增评价/收入截图的诊断保存了三次候选及反馈：第一条把评价的 movie_id 与订单的 screening_id 错误关联，还直接聚合两类事实记录，应当拒绝；后续独立聚合的候选使用 `COALESCE(净收款,0)`，原校验把补零后的有效指标误判为1027。这是关联粒度保护与表达式等价判断共同暴露的系统问题，不能靠给单条问题改词解决。

本轮增加了真实 PK/UK/FK 元数据与缓存版本、统一查询契约、跨 CTE 的指标和键血缘、通用关联放大检查及配置驱动的并列排名阶段检查。补零误拒已修正，已知可空字段的 SUM/AVG 错误等价化也被阻止。注册源缺表/缺字段最多刷新一次 Schema 并重建业务约束；权限错误不重写 SQL，刷新后失去旧口径明确拒绝。审计改为有界滚动 JSONL，保存候选、阶段、错误、SQLSTATE 和 trace_id，详见 [查询契约](query-contract.md)。

本轮最终离线测试：**208项通过**。包括非影院实体、复合唯一键、关联放大反例、合法透传和独立聚合正例、NULL反例、先后排名阶段、不同排名门槛、权限/缓存刷新边界及 HTTP 审计字段。测试不连接数据库或外部模型。

另外通过实际注册数据源执行九项数据库回归，SQL候选固定为独立基线或上一轮保留的候选，**本轮没有调用外部模型或embedding**；完整业务改写、契约、字段/业务校验、只读预检和数据库查询正常运行。评价门槛20的用例先注入诊断中保存的错误候选，确认在业务校验阶段被拒绝，再使用正确候选成功，共生成两次。其他八项使用一次候选。

## 页面再次失败：实际候选回归

用户随后两次用同一评价/收入问题查询，仍收到1027。本次日志完整保留了两个请求的各三条 SQL，确认新代码已经运行；这次不能解释为历史界面或未重启问题。候选判断如下：

| 候选 | 实际原因 | 处理 |
| --- | --- | --- |
| 第一条 | 评价与订单在同层关联，产生重复计数和金额放大 | 继续拒绝，错误给出 `join_fanout` 及对应修复步骤 |
| 第二条 | 已独立聚合；评价均分字段非 NULL、组非空且评价汇总经 INNER JOIN，AVG 的零补齐冗余，但原校验未使用该证据 | 按通用非空证明放行；未知/可空或外连接补空仍拒绝 |
| 第三条 | 收入出现 `COALESCE(COALESCE(SUM(...),0),0)`；同默认补零幂等，但原归约仅支持直接 SUM 的单层包装 | 通用多层同零默认值归约；非零默认及错误公式仍拒绝 |

进一步对原第三候选做实际只读 EXPLAIN，发现别名 `ticket_orders to` 还触发 PostgreSQL 42601。SQLGlot 虽接受该别名，PostgreSQL 要求保留字引用。现在统一在 AST 层按 PostgreSQL 标识符语义引用源别名和引用处，不按 `to` 特例替换文本。前一轮业务拒绝遮住了这一数据库错误。

本次最终**229项离线测试通过**，包含持久保存的六条真实模型候选、门槛80变体、非影院补零/AVG反例、保留字和大小写引用、针对失败原因的反馈，以及原安全规则。

另外启动了临时本机后端和本机模型响应桩：响应桩按原顺序返回保存的真实模型 SQL，外部模型/embedding 均禁用；实际 HTTP `/query` 路由、改写、修复反馈、SQL 规范化、校验、PostgreSQL 预检/查询和结果说明全部正常运行。四项回放均为 HTTP200/code0：
