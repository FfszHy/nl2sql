验证日期：2026-10-07。使用仓库默认种子生成的影院合成数据库；所有本轮模型响应来自固定候选或本机响应桩，未调用外部模型或 embedding。

## 会员问题的根因

用户再次询问“普通、银卡、金卡和白金用户，各自最喜欢哪三类电影？按实际购票人数来看，同时看看订单量和扣掉退款后的收入，全额退款的订单不算。”，请求的三条候选完全相同。

业务改写和实际 SQL 的会员值、去重顾客、电影类型、净收款及全额退款排除均正确。订单通过顾客、场次和电影的真实主键多对一关联，每条订单仍是一行；`COUNT(*) AS order_count` 在此处符合已声明口径。原校验仅能给单来源 `COUNT(*)` 归属事实表，多来源一律标为未知，导致误拒。并非再增加会员名称或退款提示就能解决。

修复使用真实完整 PK/UK，从非可空事实来源逐层证明关联目标至多一行，并沿透传 CTE 保留实际表实例。断开的唯一维度分量、循环自证、不完整复合键、一对多扇出、可空事实侧及错误关联仍拒绝。同一证明也用于原有金额和限定主键计数的粒度检查，避免“各表都唯一”被误当成“不会复制事实行”。COUNT 的严格零补齐仅在无外连接补空时按非 NULL 恒等式处理。

会员原始候选保存在 `tests/fixtures/business_sql/recorded_member_candidates.json`。新的 `count_source_ambiguity` 反馈说明无法确认计数来源的原因，审计保存结构化诊断，修复次数仍有界。

## 图表规划

查询之后由本地 `chart_planning_service` 读取原问题、SQL 字段来源、实际结果类型和指标契约，选择已有四种声明式图型。响应增加 `chart_selection`，包含意图、理由和字段画像；不额外调用选图模型。配置明确展示名、单位及可加性，未知单位保持未知，不按字段名猜百分比刻度或换算金额。

- 分类和排名只绘制主要指标，避免人数、订单量、金额、评分挤在同一轴。
- 折线要求一个真实时间序列，时间值唯一且按时间排序；月份编号不自动当作跨年份时间轴。
- 散点要求明确的两项变化数值以及单来源观察或已校验的共同实体契约；真实主键、排名、CROSS JOIN 和未知多来源粒度不能替代关系变量。
- 饼图采用保守限制：直接单事实表、单分类分组、没有筛选掉总体的 WHERE/HAVING、没有排名/内层截断、可加且非负、少量互斥类别；只能说明当前查询结果范围。去重人数、均值、比例、关联多标签、负数、零总量和截断结果不画饼图。
- 单值、空结果及证据不足时保留表格和理由；规划异常不使成功查询失败。

规划不修改、排序或重新聚合结果行。字段画像仅返回给当前请求，审计记录图型、意图和原因，不保存画像的数值或结果数组。

## 自修复预算追加调整

默认总候选预算从3提高到5（首次生成加最多4轮修复），配置范围由1–3提高到1–10；本机 `.env` 与示例配置均采用5。每个候选继续完整校验，成功立即结束，关闭重试只生成一次，Schema刷新仍最多一次，禁止写入、权限和连接类错误不因预算增加而继续重写。增加了第5候选成功、5次耗尽、关闭重试和解释接口的回归，**266项后端离线测试通过**；本轮没有调用外部模型或重新执行数据库回归。
